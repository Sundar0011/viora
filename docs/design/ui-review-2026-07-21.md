> ## ⚠ CORRECTION (2026-07-21, after implementation) — every count below is an UNDERCOUNT
>
> The census used single-line `grep`. **`dart format` wraps long argument lists at deep nesting**,
> so a large share of real occurrences span two lines and were invisible to it:
>
> ```dart
> font: GoogleFonts          fontSize:
>     .interTight(               10.0,
> ```
>
> Newline-tolerant re-scans during implementation found substantially more everywhere:
>
> | Metric | This doc claimed | Actually found |
> |---|---|---|
> | Inter/InterTight overrides — `lib/pages/group/**` alone | 19 | **75** |
> | Inter/InterTight overrides — `lib/pages/events/**` + `business/**` | 38 | **52** |
> | `fontSize: 10.0` — `group/**` | 15 | **28** |
> | `fontSize: 10.0` — `events/**` + `business/**` | 21 | **39** |
> | `fontSize: 10.0` — chat | 6 | **9** |
> | `fontSize: 10.0` — comments_page | 0 | **2** |
> | `Color(0x…)` literals — `group/**` | 14 | **59** |
>
> So the headline figures in §1 (183 Inter sites, 454 small-text sites, 33 colour literals) are
> **floors, not totals** — the true totals are roughly 2–4× higher in the worst folders. The
> *ranking* and the *conclusions* are unaffected: every finding was real and under-stated, none

## 0. What has already landed (credit where due)

The Flock design-system rework is **partially implemented** and the theme layer is in good shape:

- `flutter_flow_theme.dart` now ships **both** `LightModeTheme` and `DarkModeTheme`, and
  `FlutterFlowTheme.of(context)` correctly branches on `MediaQuery.platformBrightnessOf`.
  The "no dark mode" finding from 2026-07-19 is **fixed**.
- Typography is correctly wired to the Flock pairing: **Baloo 2** (display/headline 56/40/32/28/24/20)
  + **Manrope** (title/label/body). Correct per spec.
- `FlockGradients.sunriseLight` / `sunriseDark`, `gradient_primary_button.dart`,
  `gradient_avatar_ring.dart` exist as real reusable widgets.
- Hardcoded colors are nearly eliminated: only **33** `Color(0x…)` literals remain outside the
  theme files (down from "sprinkled everywhere"). This was done well.
- `shimmerHighlight` is a per-theme token — someone correctly noticed a white shimmer sweep
  flashes as a bright slab on a dark skeleton. That is real craft.

**So the problem is no longer the design system. It is that the screens don't consume it.**
Everything below is a *consumption* gap, not a *definition* gap.

## 2. Detailed findings

### 2.1 Safe areas — the onboarding flow is unprotected (CRITICAL)

The 2026-07-19 audit flagged `login_page` as "the single confirmed safe-area regression."
It is not single. **Every screen in `lib/pages/registration/` lacks `SafeArea`:**

```
create_account_page   email_login_page   final_steps_mail_page   final_steps_phone_page
forget_password       location_page      login_page              reset_password
splash                verify_page
```

App-wide: 78 files contain `Scaffold(`, only 68 contain `SafeArea(` — and the 10-file gap *is*
exactly the registration folder.

**Why this is the worst finding:** this is the first thing a new user sees, and it is the only
flow where every screen is affected. On a notched iPhone or an Android device with a punch-hole
cutout, back buttons and headings render under the status bar. It also affects the bottom:
"Continue"/"Next" CTAs can sit under the iOS home indicator.

**Fix:** wrap each `body:` in `SafeArea(top: true, bottom: true)`. ~10 one-line edits.
Watch for the two screens with full-bleed background images (`splash`, `login_page`) — there the
image should stay full-bleed *behind* the `SafeArea`, so wrap the content `Column`, not the
background `Container`.

### 2.2 Typography drift — Flock's fonts are not what renders

The theme is correct (Baloo 2 + Manrope). But screens re-override it back to FlutterFlow's
default Inter family. The exact pattern, from `community_widget.dart:1483`:

```dart
textStyle: FlutterFlowTheme.of(context).titleSmall.override(
  font: GoogleFonts.interTight(                       // ← replaces Manrope with Inter Tight
    fontWeight: FlutterFlowTheme.of(context).titleSmall.fontWeight,
    fontStyle: FlutterFlowTheme.of(context).titleSmall.fontStyle,
  ),
  color: FlutterFlowTheme.of(context).primaryD3,
),
```

Note what it does: it pulls weight and style *from the theme* and then throws away the *family*.
This is a leftover FlutterFlow codegen default, not a deliberate choice — and it means the app
mixes **three** typefaces (Manrope, Inter Tight, Inter) at the same hierarchy level, on the same
screen. That is the single most common cause of "this looks slightly off but I can't say why."

Distribution — this concentrates in the highest-traffic screens:

| Screen | Inter/InterTight overrides |
|---|---|
| `community_widget.dart` | 27 |
| `search_widget.dart` | 24 |
| `user_profile_widget.dart` | 14 |
| `other_profile_widget.dart` | 14 |
| `group_details_widget.dart` | 8 |
| notification, business create, event details | 6 / 6 / 5 |

**Fix:** a mechanical find-and-replace of `GoogleFonts.interTight(` → `GoogleFonts.manrope(` (and
`GoogleFonts.inter(` → `GoogleFonts.manrope(`) across `lib/**/*_widget.dart`. 183 sites, one
regex, zero layout risk (Manrope and Inter have near-identical metrics). This is the highest
visual-consistency return per minute of work in the entire codebase.

Longer-term (finding #8): the remaining ~1,577 `font: GoogleFonts.manrope(…)` overrides are
*correct in output* but redundant — they re-specify what the theme already says. They should be
deleted over time so the theme is genuinely the single source of truth, but they are not
currently causing a visible bug. Do #2 now; do #8 opportunistically when touching a file.

### 2.3 Accessibility — a complete void (CRITICAL)

```
Semantics(  →  0 hits across 469 files
tooltip:    →  0 hits across 469 files
```

Combined with an icon-only bottom nav (§2.4) and icon-only like/comment/share/report actions
throughout the feed, this means **TalkBack and VoiceOver announce nothing meaningful for the
app's primary navigation and primary actions.** A blind or low-vision user cannot use Flock.

This is also a store-review and legal-exposure risk on both platforms, not only an ethics issue.

**Fix, in priority order:**
1. Bottom nav — 5 `Semantics(label: …, button: true)` wrappers (or just re-enable the text labels, §2.4, which solves it natively).
2. Post actions (like/comment/share) — label with state, e.g. `'Like, 12 likes'` / `'Liked, 12 likes'`.
3. All bare `InkWell` + `Icon` pairs — the `AppIconButton` component proposed in the 2026-07-19 audit should bake `Semantics` in, so this gets solved once rather than per-site.
4. Avatars and post images — `Semantics(image: true, label: '<author>'s profile photo')`.

### 2.4 Bottom nav labels are still switched off

`comp_navbar_widget.dart` still has **10** dead branches:

```dart
if (false)
  Text('Home', style: FlutterFlowTheme.of(context)…)   // ×2 (active + inactive state)
if (false)
  Text('Community', …)                                  // ×2
if (false)
  Text('Post', …)                                       // ×2
if (false)
  Text('Notifications', …)                              // ×2
```

The layout scaffolding, the styling, and the strings are all already written. Someone built this
and then disabled it. Flipping `if (false)` → unconditional restores labelled navigation, fixes
the largest chunk of the accessibility gap for free, and removes the "learn 5 custom glyphs"
burden on new users — which matters a lot for this app's demographic.

**Caveat before flipping:** the bar is 54dp tall. Icon + label will not fit at 54dp. Budget
~64–68dp (Material 3 navigation bar is 80dp with labels; 64dp is the practical floor) and
re-verify each cell's tap rect is still ≥44×44 afterward. This is the one item on the Top 10
that needs a design decision, not just a code change — see §4.

There are **65** `if (false)` branches across the codebase in total (Groups: 9,
specific_user_groups: 9, search: 4, editpost: 4, comments: 4). Each one is a designed-but-disabled
feature. Worth a triage pass: each is either "should be on" (cheap win) or "should be deleted"
(dead code). Right now nobody knows which.

### 2.5 Images: no caching, no error state, no placeholder

```
Image.network        149
errorBuilder           1
CachedNetworkImage     1     ← despite cached_network_image: 3.4.1 already in pubspec.yaml
errorWidget            0
```

Three separate user-visible consequences:

1. **Perceived slowness.** Every scroll back up the feed re-downloads avatars and post images.
   On mobile data in a neighborhood app people check many times a day, this is the difference
   between "snappy" and "sluggish" — and it burns the user's data allowance.
2. **Broken-image dead zones.** A deleted/expired storage URL renders as a grey box or throws.
   With `errorBuilder` at 1/149, essentially nothing degrades gracefully.
3. **Layout jank (CLS).** No placeholder means images pop in at final size, shifting content
   under the user's thumb mid-scroll — the classic cause of mis-taps on a feed.

**Fix:** one shared `AppNetworkImage` wrapper over `CachedNetworkImage` with `placeholder:`
(shimmer, reusing the existing `shimmerColor`/`shimmerHighlight` tokens) and `errorWidget:`
(neutral avatar/photo glyph on `alternate`). Then swap 149 call sites. The dependency is already
there and paid for; this is the biggest perceived-performance win available.

### 2.6 Text below the readable minimum

```
fontSize: 10.0  →  152 occurrences
fontSize: 12.0  →  302 occurrences
```

`ui-ux-pro-max` §6 lists "body text < 12px" as an anti-pattern; 10px is well under it, and the
theme's own smallest token (`labelSmall`) is 12px — so **every 10px instance is a hand-written
value that undercuts the design system.** Concentrated in chat (`message_page`,
`comp_new_message`, `archived_chats_page`) and business screens, i.e. timestamps, unread counts,
metadata.

**Fix:** raise all `fontSize: 10.0` to the `labelSmall` token (12px). Where 12px genuinely won't
fit, the layout is too dense and should lose an element rather than shrink the type. Also check
these at Android "Largest" font scale — many sit inside fixed-height `Container`s and will clip.

### 2.7 Refresh, loading and empty states are inconsistent

| Pattern | Coverage |
|---|---|
| `RefreshIndicator` | **3** of 78 screens (home, group_details, chat) |
| shimmer skeleton | 17 screens |
| `CircularProgressIndicator` | 30 screens |
| `ModernLoading`/`SimpleLoader`/`Loader` | 11 screens |
| `CompNoDataFound` empty state | 27 screens |

Four different loading treatments coexist, so the same "waiting" moment looks different depending
on which screen you're on. And a user who has learned "pull down to refresh" on the home feed
finds it silently does nothing on Search, Notifications, Sale, My Groups, Events — that reads as
a broken app, not a missing feature.

**Fix:** the `AsyncStateView` wrapper already proposed in the 2026-07-19 audit (loading / empty /
error / data) is the right call, and this census confirms the scale of the payoff: it would
normalize 58 screens' worth of divergent state handling. Pick **shimmer** as the single loading
treatment (it's the most polished of the four already present) and add `RefreshIndicator` to
every list screen.

Also note: there is currently **no error state anywhere** — the four patterns above cover
loading, empty and data, but a failed network call has no designed UI. With 90 `catch` blocks and
37 `SnackBar` calls, most failures are being caught and shown as a transient snackbar at best, or
swallowed at worst (CLAUDE.md §5 forbids silent swallowing).

### 2.8 List performance

`shrinkWrap: true` appears **92** times, versus 49 `ListView.builder` — heaviest in Search (11),
Notifications (6), Community (6), My Group (5). `shrinkWrap: true` forces the list to build
**every** child immediately instead of lazily, which on a long feed means hundreds of widgets
built per frame. This is a leading cause of scroll jank and slow screen-open on exactly the
screens where users spend the most time.

**Fix:** where a `shrinkWrap` list is nested in a `SingleChildScrollView`, replace the pair with
a single `CustomScrollView` + `SliverList`. This is the correct Flutter pattern and removes both
the perf hit and the nested-scroll gesture conflict. Not a quick fix — schedule per screen,
starting with Search and Notifications.

### 2.9 Maintainability is the root cause of most of the above

**110 files exceed the 400-line limit in CLAUDE.md §5.** The worst:

| File | Lines | vs. limit |
|---|---|---|
| `search_widget.dart` | 9,980 | 25× |
| `my_group_widget.dart` | 6,512 | 16× |
| `community_widget.dart` | 6,413 | 16× |
| `user_profile_widget.dart` | 5,770 | 14× |
| `group_details_widget.dart` | 4,919 | 12× |
| `other_profile_widget.dart` | 4,459 | 11× |
| `notification_widget.dart` | 3,787 | 9× |

This is not a separate finding — it is *why* findings #2, #5, #6, #8 and #9 have the counts they
do. The same post card, avatar, action row and chip are re-implemented inline in every screen, so
every inconsistency is duplicated 10–30× and every fix is a 30-site edit instead of a 1-site edit.

I am **not** recommending a refactor of FlutterFlow-generated screens (CLAUDE.md §5 says do not
restructure the frontend, and a 9,980-line rewrite is high-risk for low visible gain). I am
recommending the opposite: **build the shared components once, then adopt them only in files you
are already editing for another reason.** The debt shrinks as a side effect of normal work.

### 2.10 Debug logging in shipping code

**439 `print()` calls** across `lib/`. These run in release builds, are visible via `adb logcat`
and Xcode Console, cost frame time on hot paths, and risk leaking user/session data into device
logs — which is a privacy issue, not just noise.

**Fix:** replace with a `debugPrint` wrapper gated on `kDebugMode`, or delete. Mechanical; also
worth a `flutter analyze` lint rule (`avoid_print`) so they can't come back.

## 4. Decisions I need from you (CLAUDE.md §7 — not making these silently)

1. **Bottom nav labels.** Re-enabling them requires growing the bar from 54dp to ~64dp, which
   shifts every screen's bottom inset. Options: (a) labels on, bar to 64dp — best for usability
   and accessibility; (b) keep icon-only, add `Semantics` labels only — zero layout change,
   fixes screen readers but not new-user comprehension. I recommend (a).
2. **The 65 `if (false)` branches.** These are designed-but-disabled features across Groups,
   Search, Comments, Edit Post. I can triage and report what each one is, but deciding whether a
   given feature *should* be live is a product call, not mine.

   dropping the element or letting the row grow taller?
